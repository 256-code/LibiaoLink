# ADR-004 数据库与数据访问：PostgreSQL 18 + Drizzle ORM + 显式 SQL 迁移

- 状态：草案（Proposed）｜评审：lan、px｜随 PR 合并 main 后转「已采纳（Accepted）」
- 日期：2026-09-18｜决策人：wmj（技术负责人）
- 依据：技术设计v0.1-选型分析.md §0.1、§4.4、§4.20、§5（#4、#5）；CONTRIBUTING.md §14

## 背景

本项目需要：强约束（NOT NULL / CHECK / 部分唯一索引 / 复合外键）、JSONB 自定义字段、窗口函数与汇总、原生队列能力（SKIP LOCKED）、中文检索（PGroonga）、可回滚的显式迁移历史。300 人规模数据量在百万行级，不构成拆分数据库的理由。

## 决策

- 数据库：**PostgreSQL 18.x**（部署时锁定精确补丁），一库承担五种角色：事务库、队列与调度表、搜索索引、统计汇总、审计留痕。
- 数据访问：**Drizzle ORM + 显式 SQL 迁移**（继承旧设计）；迁移器与迁移脚本落 database/（阶段 5 · DB 基线）。
- 自定义字段：JSONB + 字段定义表驱动校验；高频过滤字段用生成列 + B-tree 索引，低频用 GIN；报表经视图 / 汇总表，不直接在 JSONB 上做重聚合。
- 大表策略：审计日志、消息记录、日报三张表单表超 500 万行时按年分区；迁移遵循 expand / contract，已合并迁移不可修改。

## 备选与不采用原因

- MySQL 8.x：CHECK 与部分索引能力弱、无物化视图、JSON 能力与生态经验不如 PG（仅当公司 DBA 标准强制且不可协商时切换）。
- Prisma：开发体验好，但复杂 SQL、JSONB 与约束表达力弱。
- Kysely：纯查询构建器，缺迁移与关系建模约定。

## 影响与后果

- 单库多能：一期不引入搜索集群、缓存集群，运维面最小。
- Drizzle 保留 SQL 控制力：锁、索引、约束全部显式可审。
- 迁移是独立受限任务，应用进程不得在启动时自动改结构（CONTRIBUTING.md §14）。

## 切换触发条件

公司 DBA 标准强制 MySQL 且不可协商（切换成本高，需整体重估 ADR-005 的队列实现）。
