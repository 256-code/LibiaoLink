# ADR-013 部署与容量起点：Docker Compose 单机 + Nginx

- 状态：草案（Proposed）｜评审：lan、px｜随 PR 合并 main 后转「已采纳（Accepted）」
- 日期：2026-09-18｜决策人：wmj（技术负责人）
- 依据：技术设计v0.1-选型分析.md §0.1、§4.17、§4.18、§5（#14）

## 背景

300 人规模、一期只服务实施部门，无弹性伸缩与多租户需求；团队 3 人且运维由前端负责人兼任，运维复杂度必须最小。

## 决策

- **部署形态**：Docker Compose 单机，Nginx 唯一暴露端口；组件：Nginx / api / worker / converter / PostgreSQL / MinIO。
- **容量起点（估算，需实测校准）**：
  - 试点（实施部门，80 用户以内）：1 台 8C16G + 500G SSD 系统盘 + 2TB 数据盘，全部组件同机；
  - 生产（300 用户）：应用节点 8C16G + SSD；存储节点 4C8G + 2~4TB（MinIO 独立盘 + 异地备份）；数据库可与应用同机；
  - converter 限额 2C4G、并发 2~4，防止转换任务吃光整机。
- **生产门禁（不可省）**：容器非 root；镜像精确版本 + digest；迁移独立任务执行（API 不自动迁移）；Secrets 走文件挂载；CPU / 内存 / pids 限额；数据库连接池有界。
- **可用性口径**：「核心工作时间可用性 ≥ 99.9%」需先定义统计口径——工作日 8:30–18:30（按工作日历）、按月统计、剔除提前 24 小时以上通知的计划维护（每月不超过 1 次）；单机现实下建议按「计划外中断次数 + 恢复时长」联合验收（Q19，验收前与业务 / IT 书面确认）。
- **备份与恢复**：数据库每 12 小时加密备份（RPO ≤ 24h、RTO ≤ 2h，以实测为准）；文件每日增量异地同步；每月一次恢复演练（数据库 + 文件一致性抽检）。

## 备选与不采用原因

云托管 / K8s：无弹性伸缩需求，成本与复杂度不划算。

## 影响与后果

- 单机部署下「可用性」与「恢复时长」强绑定，必须靠备份与演练兑现承诺。
- 容量数字是估算起点，需用真实数据校准后再做容量承诺。

## 切换触发条件

用户量或可用性要求显著提升（全公司多部门使用、要求多实例与滚动升级）时，评估云托管 / K8s。
