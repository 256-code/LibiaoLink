# ADR-018 后端实施：里程碑 M0~M8 + 八步卡片流水线

- 状态：草案（Proposed）｜评审：lan、px｜随 PR 合并 main 后转「已采纳（Accepted）」
- 日期：2026-09-18｜决策人：wmj（技术负责人，随本 PR 评审确认）
- 依据：技术设计v0.3-实施与验收.md §1~§3；团队分工.md §4~§6；CONTRIBUTING.md §5、§15、§17

## 背景

契约包（g2）、数据库基线（g3）、server 骨架（g4）、CI（g5）与 ADR-001~017（g1）已落地，功能书与前端页面已先行；但后端还缺「从契约到验收」的统一执行流程：

1. 卡片粒度、依赖顺序、并行边界没有共同定义，里程碑之间容易互相等待或返工；
2. 契约、迁移、模块、测试、文档的完成标准不齐，存在「代码先推、文档滞后」的风险；
3. 功能书只写到业务口径，前端已实现的页面又反向暴露了接口与数据模型缺口，需要固定的口径落点。

团队 3 人 + AI 代理，一期按 4~6 个月规划；文件管道与自动化是并行瓶颈（技术设计v0.1-选型分析.md §7.5.1）。

## 决策

**1. 里程碑 M0~M8**（技术设计v0.3 §2~§3）：

- M0 口径冻结与种子 → M1 身份与平台底座 → M2 项目纵切 → M3 任务纵切 → M4 文件与预览 → M5 自动化与通知 → M6 日报 / 问题 / 干系人 / 工作台 → M7 搜索 / 仪表盘 / 导出 → M8 迁移与上线；
- 关键路径 M0 → M1 → M2 → M3 → M4 → M5 → M8；M6 在 M3 后与 M4 / M5 并行，M7 在 M4 / M6 数据就绪后并行；
- 九项 PoC（团队分工.md §6）按 v0.3 §2.4 落点纳入对应里程碑验收。

**2. 卡片是唯一交付单位**：每张卡必须走完八步——口径确认 → 契约 → 迁移 → schema → 模块实现 → 测试 → 联调 → 文档与推送；缺一步不算完成。

**3. DoR / DoD 增补**（在 CONTRIBUTING.md §17 之上）：

- DoR：口径已决 + 依赖已合并 + 契约草案已评审 + 测试数据 / 样本就绪；
- DoD 增补两条：空库迁移一次跑通且 schema 无漂移；涉及数据的接口至少各一条允许与一条拒绝用例（拒绝为 404 语义）。

**4. 口径未决项**按 v0.3 §7 十五项清单逐项关闭（ADR / 业务确认 / PoC 结论），未决前按建议值先行并在决议记录标注「可修订」。

## 备选与不采用原因

- 按模块交付（先建全部表、再统一写接口）：接口无法尽早联调、风险后置，不采用；
- 按人分工自由推进（只定模块不定流程）：依赖与验收口径不齐、返工成本高，不采用；
- 先完成全部详细设计再开发：功能书与前端已先行，等待成本高且无法吸收实现反馈，不采用。

## 影响与后果

- 正面：交付粒度统一、依赖清晰、并行边界明确，前端可按里程碑逐步接真；
- 负面：卡片模板与证据要求带来单卡开销；M0 需要约一周口径冻结，短期不产出代码；
- 约束：含迁移的卡片必须空库验证；权限矩阵入 CI；文档同步与开发日志属于 DoD 组成部分。

## 切换触发条件

团队扩至 4 人以上、引入独立 QA / 发布列车，或需要多版本并行发布时，重新评估卡片流水线与里程碑划分。
