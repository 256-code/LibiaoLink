# ADR-005 队列与调度：PostgreSQL 原生（Outbox + SKIP LOCKED + advisory lock）

- 状态：草案（Proposed）｜评审：lan、px｜随 PR 合并 main 后转「已采纳（Accepted）」
- 日期：2026-09-18｜决策人：wmj（技术负责人）
- 依据：技术设计v0.1-选型分析.md §0.1、§4.5、§4.13、§5（#6）

## 背景

本项目存在外部副作用（企微消息、站内信、后续邮件 / ERP 同步）：进程崩溃、渠道限流、网络抖动都可能丢消息。旧项目所有副作用都是数据库写入、事务即可保证；本项目必须「至少一次投递 + 消费幂等」，Outbox 因此是强制项。

## 决策

一期**零新增中间件**，用 PostgreSQL 原生实现队列与调度：

- 表：outbox（事件、payload、状态、attempts、next_attempt_at、locked_at / locked_by、last_error）与 job / rule 表；索引 (status, next_attempt_at)。
- 领取：批量 UPDATE ... WHERE id IN (SELECT ... FOR UPDATE SKIP LOCKED) RETURNING；locked_at 可见性超时自动回 pending，防止 worker 崩溃丢任务。
- 重试：指数退避 + 最大次数 + 死信（failed）标记并告警；成功行按保留期（约 90 天）清理，观察表膨胀。
- 幂等：投递键 = 规则 ID + 实体 ID + 触发窗口（支持状态回退再生窗口）。
- 调度：pg_advisory_lock 选主、单活调度器；任务定义入 DB，每分钟 tick，支持错过补发（last_run_at 与窗口比对）。
- 限速：渠道级令牌桶（企微群机器人 20 条 / 分钟，待实测）在 worker 侧实现。

## 备选与不采用原因

- Redis + BullMQ：生态成熟（限速 / 延迟任务方便），但新增一个有状态组件（备份 / 监控 / 调优），当前量级不必要——设阈值，触发再引入。
- RabbitMQ / Kafka：无跨系统事件流与高吞吐需求，收益为零、成本为正。

## 影响与后果

- 业务写入与待投递消息同事务，提交即不丢；重复由幂等键消除。
- 队列与业务同库：备份、恢复、一致性演练是一件事（与 ADR-006 的备份口径衔接）。
- 新的观测对象：Outbox 积压量与最老消息年龄纳入告警（技术设计v0.1 §4.17）。

## 切换触发条件（引入 Redis / Valkey，并评估 BullMQ）

1. 出现多实例部署且需要共享锁 / 缓存；或
2. 持续外发速率超过 5 条 / 秒；或
3. PG 队列 / 锁竞争在压测中成为瓶颈。

任一条成立即引入，并同步升级本 ADR。
