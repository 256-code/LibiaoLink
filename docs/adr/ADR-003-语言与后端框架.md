# ADR-003 语言与后端框架：TypeScript + NestJS 12

- 状态：草案（Proposed）｜评审：lan、px｜随 PR 合并 main 后转「已采纳（Accepted）」
- 日期：2026-09-18｜决策人：wmj（技术负责人）
- 依据：技术设计v0.1-选型分析.md §0.1、§4.3、§4.20、§5（#3）

## 背景

团队为 2 后端 + 1 前端 / 运维，且大量工作由 AI 代理协同完成；旧项目的工程规范（契约、迁移、权限矩阵、AI 规范）已验证可整体平移。CPU 密集任务（文档转换、打包、报表）本就交给外部进程 / 容器。

## 决策

- 语言：TypeScript（严格模式）。
- 后端框架：NestJS，api 与 worker 同栈双入口。
- 版本：新项目**直接评估并采用 NestJS 12.x**，不继承旧项目 11.2.3 的历史锁定；阶段 0 完成兼容性 PoC 后锁定精确版本（见 ADR-017）。

## 备选与不采用原因

- Java + Spring Boot：文件 / Office 生态最强，但团队与 AI 工作流断层；仅当公司 IT 标准强制或确认由 Java 团队接手时切换（架构形态不变，仅替换语言层实现）。
- Go：Web 与后台工程生态弱于前两者，收益不明显。
- Python：类型、迁移、构建等工程约束成本高，团队无延续性。

## 影响与后果

- 前后端同语言：契约（Zod）与类型可在 shared/ 单源复用。
- 语言性能不是瓶颈：CPU 密集任务在 converter 容器执行，api / worker 只做编排。
- 更换语言的代价被架构隔离：进程边界清晰，替换语言层不影响数据模型与协议。

## 切换触发条件

公司 IT 标准强制 Java 技术栈，或确认后续由 Java 团队接手维护与 ERP 中间件对接。
