# ADR-002 总体架构形态：模块化单体 + api / worker 多进程 + 转换容器

- 状态：草案（Proposed）｜评审：lan、px｜随 PR 合并 main 后转「已采纳（Accepted）」
- 日期：2026-09-18｜决策人：wmj（技术负责人）
- 依据：技术设计v0.1-选型分析.md §0.1、§4.2、§5（#2）、§7.1；技术设计v0.2-架构与数据模型.md（架构篇）

## 背景

文件转换是 CPU 密集型任务（LibreOffice headless 等），与 HTTP 接口同进程会互相阻塞；定时与投递任务在重启后不能丢语义；300 人规模没有高并发与独立扩缩容需求。

## 决策

- **模块化单体**：单一代码库、同一仓库演进，边界按模块划分，不在仓库层面拆服务。
- **多进程运行时**：
  - api：HTTP 接口、鉴权、权限判定、业务事务、预签名 URL，不做重活；
  - worker：Outbox 投递、定时调度、规则执行、转换编排、报表；
  - converter：无外网、非 root、只读根文件系统的转换沙箱。
- **数据与文件**：PostgreSQL（事务 + 队列 + 调度）与 MinIO（S3）使用独立数据盘。
- **入口拓扑**：Nginx 唯一暴露端口（静态 SPA / api / 文件鉴权代理）；一期由 Docker Compose 单机承载（见 ADR-013）。

## 备选与不采用原因

- 纯单体单进程：转换阻塞 API、重启丢失定时语义。
- 微服务：无独立扩缩容需求，分布式事务与联调成本为纯负收益。
- Kubernetes：无弹性伸缩与多租户需求，单机 Compose 运维成本更低。

## 影响与后果

- 进程边界即故障边界：转换沙箱被攻破或崩溃不波及 api 与数据层。
- 同代码库多入口：共享领域模型与契约（shared/），无跨服务联调成本。
- 升级路径明确：需要多实例时先加 Redis 与共享调度（ADR-005 触发），再评估服务拆分。

## 切换触发条件

需要多实例部署或独立扩缩容时，按 ADR-005 先引入 Redis / Valkey 与共享调度，再评估拆分服务。
