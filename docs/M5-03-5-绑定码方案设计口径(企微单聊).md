# M5-03-5 绑定码方案设计口径（企微 ID 绑定 · 激活与寻址）

> 归属：**lan（notify / 平台线）**起草 · 跨线改动一律「**lan 代记 + 相关负责人复核**」（本口径涉及 `frontend/` = px 线、契约与 ADR = wmj 线）。
> 状态：**设计口径 v1.0 · 2026-10-16 · 待评审 · 未实现**（评审路由：wmj = 技术可行性 / ADR-033 增补；px = 前端可行性与实现一致性）。
> 上位口径：`docs/M5-03-单聊改智能机器人执行计划(企微单聊).md`（P1 ~ P7 定案）、`docs/adr/ADR-033-企微消息通道改由智能机器人承接.md`。
> 本口径的变更点：把「激活」从**任意单聊消息**收敛为**发送绑定码**（用户成本不变：每个用户对每个机器人一次），并据此统一单聊寻址键。

## 1. 背景与硬约束

- 企微智能机器人回调的 `from.userid`：**若机器人创建者不是企业超级管理员，则为企业主体下的加密 userid（open_userid）**（官方「接收消息 / 接收事件」原文；本仓实测见 §2）。
- 本项目**无法取得企微后台管理员权限**，因此两条替代路走不通：
  - 把机器人创建者改为企业超级管理员（回调即给明文 userid）；
  - 用自建应用调 `POST /cgi-bin/batch/openuserid_to_userid` 做密文 → 明文归一（需自建应用 access_token + 成员在该应用可见范围内）。
- 故 **明文 userid ↔ 密文 open_userid 的映射只能由用户侧交互产生**——这是本方案要解决的唯一问题。
- 产品口径（已定）：接受「每个用户对每个机器人先激活一次」的成本；**未激活推送不再是目标**。

## 3. 目标形态

**绑定（一次性 · 用户驱动）**
1. 用户在系统内请求绑定 → 服务端生成**绑定码**（6 位数字、TTL 10 分钟、一次性、与登录态 `user_id` 绑定）；
2. 用户在与机器人的**单聊**里发送该码；
3. 长连接回调 ingest 命中码 → **同一事务内**写绑定（库内用户 ↔ open_userid）+ 标记码已用 → 用 `response_url` 回「绑定成功」。

**投递（常态化）**

4. 单聊推送地址一律取绑定行的 open_userid；无绑定行 = 不可投递（§6）。

状态机要点：
- 绑定即激活：发码本身就是「给该机器人发过消息」，会话激活态与绑定天然同源；
- 换绑：同一 `user_id` 再次命中新码 → 覆盖旧绑定（旧行处置见 §8）；
- 幂等：回调可能重复投递（官方 `msgid` 排重），绑定写库幂等；已用码再次命中 = 视为已用。

## 4. 数据模型（待评审）

**复用 `wecom_aibot_dm_activations`（迁移 0048）= 地址簿 + 激活登记 + 绑定三合一**

- `wecom_userid` = 回调 `from.userid` 原文（密文 open_userid）· 唯一（沿用）；
- `user_id` = 库内用户；本方案下**只有 `user_id` 非空的行才是可投递地址**；
- `first_activated_at` / `last_message_at`（沿用）+ 新增 `bound_at`（绑定确立时间）。

**新增绑定码表 `wecom_id_binding_codes`（迁移 0049 起）**

| 列 | 说明 |
|---|---|
| `id` | 主键 |
| `code` | 6 位数字串（唯一） |
| `user_id` | 发起人（FK → `users`） |
| `status` | `pending` / `used` / `expired` |
| `expires_at` / `used_at` / `created_at` | 时限与审计 |
| `used_wecom_userid` | 实际使用该码的 open_userid（绑定/换绑排查） |

约束与规则：
- 同一 `user_id` 仅允许一个 `pending` 码（重发生效最后一条、旧码作废）；
- 生成频率限制（建议 3 次/小时/用户）；
- `code` 唯一 + 一次性；
- 明文 userid（`users.username` = SSO 口径 Casdoor Name）**保持不变，且不再作为发送地址**。

## 5. ingest 分支口径

处理条件：`cmd = aibot_msg_callback` 且 `chattype = "single"` 且 `msgtype = "text"`。

- 群聊（`chattype = "group"`）**一律不绑定**；
- 正文归一：trim → 去 `@<机器人名>` 前缀 → 提取码（形态见 D3）；
- **正文不入库、不落日志**：只记「绑定事件 + userid 掩码 + 结果」（CONTRIBUTING §12）；
- 未命中码的单聊消息：沿用现有「任意单聊消息 = 激活登记」——该行可能无 `user_id`，**不可作发送地址**（待定项 D1）；
- 反馈（`response_url`）：命中 → 「绑定成功」；码过期 → 「码已失效，请重新获取」；该 userid 已绑定 → 「已绑定」；未命中任何码 → 不回复（防探测）。

## 6. 投递前判定与失败处置

- 收件人无绑定行（或 `user_id` 为空）→ **不发帧**，按 `permanent` 收口：`notify_deliveries.state = dead` + C5-04 站内信降级，降级前缀改为**绑定指引**（终稿待定 D4）；
- 有绑定行 → 正常发帧；846607 按 §7 分流；
- 页面侧：设置页显示绑定态（已绑定 / 未绑定 + 获取绑定码入口）；未绑定用户的通知相关页面给「未绑定企微」提示（`frontend/` = px 线，需求由本口径提出，见 §11）。

## 7. 846607 分流口径（激活表职责）

- 职责不变：846607 双语义（会话未激活 / 发送超频）靠激活表命中分流——命中 → `rate_limited` → `deferred`（不消耗重试次数）；未命中 → `permanent` → `dead` + 降级。现实现：`server/src/modules/notify/notify.dm.service.ts`（读表 / 分流）+ `wecom.errors.ts`（`classifyWecomErrcode`）。
- 本方案增益：绑定行必带 `user_id`，命中判定不再出现「只有密文、没有主」的模糊行。
- **核心实现变更**：单聊发送地址由 `users.username` 改为**绑定表的 `wecom_userid`**；`users.username` 只保留 SSO 与 `wecom_app` 备用通道用途。

## 8. 换机器人 / 换企业

- **地址与群绑定可复用**：`open_userid`（E6）与群 `chatid`（E7）跨机器人稳定 → 无需换绑、无需清空地址簿。
- **激活态必须按机器人重置**：「会话未激活」是针对具体机器人成立的。若换机器人后保留旧行，846607 会被判成「超频」→ `deferred` 反复延期重排（deferred 不消耗重试次数），既不 `dead` 也不降级，消息在队列里空转且用户无提示——比直接失败更糟。
  - 过渡落地：换机器人时清空 `wecom_aibot_dm_activations`；
  - 正式方案：给该表加机器人维度（`(bot_id, wecom_userid)` 唯一）——待定项 D2。
- **换企业（corpid 变化）**：open_userid 与 chatid 均可能改变 → 必须重新绑定、重新绑定群。

## 9. 安全与隐私

- 绑定码 = 短时凭据：一次性、TTL、频率限制、与登录态绑定；日志只留掩码；
- 正文解析面最小化：只做码匹配，不落库、不进日志；
- 误绑防护：码被他人企微账号发出 → `used_wecom_userid` 留痕可审计；提供解绑入口（D6）；
- 群聊不绑定：E3 的 `@机器人名` 前缀正是群场景特征，解析与分支双重排除。

- **单测 / 回放**（无网络、可入 CI）：ingest 分支（群聊不绑定 / `@` 前缀容错 / 码过期 / 码复用 / 回调重复投递幂等）；发送分支（无绑定行 → dead + 降级；有绑定行 → 正常帧；846607 命中与未命中两分支）。

- **门禁**：`vitest` / `check:boundaries` / `typecheck` / `build` / 相关回放脚本退出码。
